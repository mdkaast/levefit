# Технический аудит Levefit

Дата: 26.10.2026. Основа: код в ветке `feature-adaptive-core` (поверх `feature-onboarding-wheels`), пакет `Levefit_package.zip` (бэклог A–M, 33 макета, каталог, правила). Бэклог писался по 18 скриншотам без кода: часть его пунктов уже сделана, часть сделана иначе. Ниже факты по коду.

## 1. Стек и окружение

| Слой | Что есть |
| --- | --- |
| Фронтенд | React + TypeScript + Vite, `@telegram-apps/sdk`, один файл стилей `styles.css`, тексты в `i18n.ts`. Нет роутера и стейт-библиотеки: экраны переключаются состоянием в `App.tsx`. Тесты vitest (21) |
| Бэкенд | FastAPI, SQLAlchemy 2 (синхронный), Alembic (миграции 0001–0012), Pydantic. Тесты pytest (165 + 1 пропущен) |

| ИИ | `app/ai/`: интерфейс `LLMProvider`, Anthropic (`claude-opus-5-5`), структурный ответ + `safety.py`. Ключ на сервере не задан |

| Хостинг | VPS Fornex: 1 vCPU, ~1 ГБ ОЗУ + 1 ГБ свопа, 10 ГБ диска. Docker Compose, общий Caddy, Let's Encrypt. Выкладка `scripts/deploy_vps.sh` |
| CI | GitHub Actions: линтеры и тесты api, bot, web |

Состояние веток: сервер сейчас работает на `feature-onboarding-wheels`; `main` отстаёт (коммит `4fdbdb1`), в него не влито ничего из трёх веток: `feature-ai-coach-knowledge`, `feature-onboarding-wheels`, `feature-adaptive-core` (последняя содержит две предыдущие). Правило владельца: в `main` только по просьбе.

## 2. Ключевые модули

- `apps/api/app/game_rules/` — чистые функции правил (уровни, XP, серии, ранги, задания, напоминания) и один `config.py` с константами.
- `app/game.py`, `app/tasks_routes.py` — начисление XP и задания; `app/workouts.py`, `app/metrics.py` — тренировки и вес.
- `app/ai/` + `app/adjust.py` — ИИ-корректировка после тренировки; `app/progress.py` — история, расчётный максимум, плато, стартовый план.
- `app/coach.py`, `app/admin.py` — правила тренера, оценки, админ-панель (аналитика, ИИ).
- Веб: `screens/` (Home, Onboarding, WorkoutScreen, Progress, Profile, Admin, AdjustmentView), `components/` (WheelPicker, силуэт мышц, аватар).

## 4. Расхождения между макетами/промптом и текущим кодом

1. **Навигация:** 3 вкладки (Главная, Прогресс, Профиль) + «Админ» у владельца; нужно пять (Сегодня, Тренировки, Питание, Прогресс, Атлет).
2. **Дизайн-токены:** другие значения; единый источник есть только как CSS-переменные в `styles.css`.
3. **Онбординг:** 9 шагов (имя, пол, возраст, рост/вес, цель, опыт, образ жизни, режим, мышцы); в макетах другой порядок и направления.
4. **Каталог:** `exercises` — `id int`, `name`, `category`, `muscle_group`, `owner_id`; в каталоге строковые slug, паттерны, мышцы с весами, инвентарь, шаги.
5. **Мышцы:** шесть групп при онбординге; макеты — восемь групп на силуэте и расширенный набор.
6. **Движок:** см. следующий раздел.

## 5. Главное архитектурное решение: движок на правилах

Промпт и бэклог: вес, повторы, подходы, разгрузку, возврат после перерыва считает детерминированный код; ИИ-тренер объясняет, отвечает на вопросы, предлагает замены; журнал решений сверяем с тем, что сказал тренер.

Сейчас наоборот: ИИ выдаёт числа, а `safety.py` их ограничивает. Переход:
- новый пакет `app/engine/` (чистые функции, без БД и сети): двойная прогрессия, шаг по типу нагрузки, округление под инвентарь, e1RM (Эпли до 10 повторений) с поправкой на RIR, застой, разгрузка, возврат после перерыва, «плохой день»;
- `progress.py` (e1RM, плато) и проверки `safety.py` переиспользуются как основа;
- `AiAdjustment` остаётся таблицей журнала; в неё добавляются версия правил, входы и выходы движка; ИИ получает уже принятое решение и пишет объяснение, число не меняет;
- если ИИ недоступен, решение и короткое шаблонное объяснение всё равно выдаются (сегодня при отсутствии ключа получаем 503, это перестанет быть блокером).

## 6. План миграции схемы

Принципы: только добавляющие миграции с `downgrade`, перед каждой разовый `pg_dump`, существующие тренировки и подходы не трогаются.

1. **Каталог.** К `exercises` добавляются `slug` (уникальный), `name_en`, `movement_pattern`, `level`, `load_type`, `load_increment_kg`, `trackable_for_e1rm`, `caution_flags`, `source`, `verified`. Новые таблицы `muscle`, `exercise_muscle`, `equipment`, `exercise_equipment`. 24 существующих упражнения сопоставляются с каталогом по названию и **сохраняют свои `id`**, чтобы не потерять историю; пользовательские упражнения остаются как есть.
2. **Шаблоны.** `program_template`, `template_day`, `template_slot`, `selection_matrix` (цель × дни × уровень × инвентарь).
3. **План и решения.** `user_direction`, `user_program`, `planned_week`, `planned_session`, `decision_log` (версия правил, входы, результат, причина); `ai_adjustments` не удаляется.
4. **Профиль.** Новые поля: направления, инвентарь, дни недели, длительность, ограничения, `sex_silhouette`, `reduced_motion`, `haptics`.
5. **Питание, рецепты, подписки** — отдельными миграциями в своих фазах.
6. **Скрипт переноса** для существующих пользователей (сейчас 4 реальных аккаунта): восстановить значения по умолчанию для новых полей без повторного онбординга; при желании предложить уточнить профиль на экране «Профиль».

## 7. Технический долг, которого нет в бэклоге

- Нет роутера: добавление пяти вкладок и вложенных экранов потребует лёгкого роутера или аккуратного конечного автомата; предлагаю внутренний стек экранов без внешней библиотеки.
- Один файл `styles.css` растёт; для токенов и компонентов нужен разбор на слои (токены, базовые стили, компоненты).
- Синхронный SQLAlchemy на 1 vCPU: для выборок питания и каталога достаточно, но тяжёлые отчёты придётся делать в фоне.
- Рассинхрон документов: `docs/handoff.md` описывает состояние до админки, плато и образа жизни.
- CRLF/LF: на Windows файлы пишутся с CRLF; правки идут через скрипты, чувствительные к концам строк (`.gitattributes` задаёт LF для `.sh`, `.caddy`).
- Нет регулярных бэкапов и проверки восстановления; нет ограничения запросов на уровне API.
- Docker-compose для локального запуска не проверен (на машине нет Docker).

## 9. Риски

- **Сервер:** 1 vCPU, ~1 ГБ ОЗУ, 10 ГБ диска. Каталог упражнений и шаблоны помещаются; база продуктов (сотни тысяч записей), фото рецептов и GLB-модели потребуют диска и, вероятно, более крупного тарифа. Статику 3D и фото лучше отдавать отдельным хранилищем.
- **Макеты:** файлы `.dc.html` подключают `./support.js`, которого в пакете нет, поэтому отдельно в браузере они не отрисовываются. Вёрстку и поведение можно читать из исходного HTML и `MOCKUPS_SPEC.md`, но визуальной сверки «пиксель в пиксель» без этого файла не будет.
- **3D-модели:** лицензия и сегментация мышц — отдельный вопрос; пока делаем заглушку с единым контрактом `getBodyModel(sex)`.
- **Контент:** бег, йога, кроссфит, функциональный тренинг не исследованы до уровня силовых программ; будут шаблоны с `verified: false`.
- **Telegram Stars:** потребуют изменений в боте (обработка платежей) и серверной проверки статуса.
- **Единая ветка с сервером:** на сервере работает не `main`; пока ветки не слиты, любая новая работа должна строиться поверх `feature-adaptive-core`.
